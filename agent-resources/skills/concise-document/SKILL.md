# concise-document

迷ったら削る。 文書は読み手が判断・実行・検証するための最小限の情報に絞る。情報を網羅したことではなく、短時間で使えることを品質とする。

## 書き方

- 冒頭3行以内で要点を示す。 方針・提案なら結論と採用理由、調査なら結果、仕様なら定義する振る舞い、手順なら実行前提と達成状態を書く。
- 見出しは必要なものだけ。 短い方針・提案書は本文3〜5セクションを目安とし、無理に増やさない。背景・目的・対象読者・用語・経緯・まとめ・将来構想は原則省略する。理解や判断に不可欠な場合だけ加える。
- 採用した案と理由を書く。 代替案が判断に必要なら「案 | 却下理由」の2列で示す。自明なメリット・デメリットや、採らなかった案の詳細は書かない。
- 範囲を明確にする。 設計・提案では、誤解されやすい対象外だけを Non-goals に書く。スコープ外の一般論を羅列しない。
- 同じ内容は一度だけ。 別の章で言い換えず、必要なら節・ID・既存の資料へリンクする。コードやdiffから自明なファイル一覧・手順は書き写さない。
- 一項目一論点。 原則一文で言い切る。「〜することができる」、抽象的な美点（「保守性が上がる」など）、不要な前置きは省く。図・表・例は文章より短く明確になるときだけ使う。

## 既存文書を短くするとき

1. 残す: 決定、非自明な理由、仕様・入出力、制約、重要な例外、受入条件、検証方法、未決事項のうち読み手に必要なもの。
2. 削る: 自明な背景、重複、検討の時系列、レビュー履歴、採用しない案の長い説明、用途のない将来案、空の見出し。
3. 統合する: 同じ内容を扱う章・表・箇条書き。段落を一律に要約するのではなく、不要な単位ごと削除してから短文化する。
4. 照合する: 原文の事実・数値・条件・確度・決定状態が変わっていないか確認する。参照先に委ねるのは既存の有効な資料があるときだけ。別文書を勝手に増やさない。

## 優先する制約

- 指定された様式、他スキルの必須契約、実装に必要な受入基準・依存関係・テスト・リスク対策は削らない。省略は表現と重複から始める。
- 事実と推測、決定と提案、完了と未完了を混同しない。根拠のない補完をしない。
- 最後に各見出し・段落へ「なくても同じ判断・実行・検証ができるか」を問う。できるなら削る。

例: 「AとBにはそれぞれ利点があります。Aは将来的な柔軟性が…」ではなく「Aを採用。Bは既存APIとの互換性を壊すため却下。」と書く。

完成文書を返す。変更履歴や長い自己評価は、依頼されたときだけ添える。
