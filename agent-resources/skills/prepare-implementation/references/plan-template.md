# Plan Template

plan.md を読む、または書く直前に読む。
plan.md は作業単位の「何を・なぜ」「どう・どの順で」と進捗の source of truth であり、このファイルが書式の正典である。

## Path convention

```text
.ai-local/plans/<plan-id>/<YYYYMMDD>_<agent-name>_<slug>.md
```

チケットをソースとする場合は、`ENG-123` や `github-123` のようなチケット ID を `<plan-id>` に使う。
ユーザー依頼をソースとする場合は、`request-<slug>` を使う。
sliced の変更でも plan.md は1つにする。

## 状態

- single では、ヘッダーの `Status` が `draft` か `approved` を表す。
- sliced では、ヘッダーの `Status` を `sliced` にし、`## スライス` の各スライスが `outline`、`draft`、`approved` のいずれかを持つ。
- `outline`: スライスの範囲だけを決め、タスクを詳細化していない。
- `draft`: タスクを詳細化中、または最終承認前である。
- `approved`: G2 で最終承認を得た。
- 実装の完了は `## タスク` のチェックボックスで表す。sliced では、スライスのタスクがすべてチェック済みならそのスライスを完了とする。

## 再開

plan.md を全文読み、次の順で再開する Step を決める。

1. 対象を決める。single では plan 全体を対象にする。sliced では、未完了のスライスのうち blocked_by がすべて完了している最初のスライスを対象にする。全スライスが完了していれば、完了を報告して停止する。
2. 対象が `approved` で未チェックのタスクがある場合は、Step 6 で実装開始か引き継ぎかを確認する。
3. 対象が `outline` の場合は、`draft` にして Step 2 から対象スライスを詳細化する。
4. `## 未決事項` が残っている場合は、Step 2 の質問ラウンドから再開する。
5. `## AIレビュー` に対象の指摘があり、採否が決まっていない場合は、G2 から再開する。
6. それ以外は Step 4 の self-check から再開する。

## 拘束力

承認済みの plan.md のうち、次の項目を拘束項目とし、implement-plan が contract として扱う。

- `## 要件`、`## 決定事項`、`## 設計`
- `## 変更面`、`## 展開順`、`## まれなケースの扱い`
- `## タスク` のタスク構成と、各タスクの `implements`、`depends_on`、`done_when`、`test` の検証する振る舞い
- `## テスト方針` の検証する振る舞いと edge case

次の項目は非拘束とし、実装者が実態に合わせて読み替える。

- `test` と `## テスト方針` の command
- `## 影響範囲と既存パターン`
- `## AIレビュー`、`## 実行メモ`

## Template

```markdown
# <タイトル>

- **Plan ID:** <plan-id>
- **ソース:** GitHub | Linear | User request — <完全な URL、ID、または元依頼の短い引用>
- **Status:** draft | approved | sliced
- **Risk:** low | medium | high — <理由>
- **作成:** <AI agent 名 / モデル ID>、<YYYY-MM-DD><上位推論モデルを使えなかった場合は、その旨と品質上の不利益>

## 要件
- **ゴール:** <完了状態を1〜3文で書く。>
- **受入基準:**
  - AC1: <観測可能でテスト可能な成果。ユーザー依頼から推定したものは末尾に (推定) を付ける。>
- **制約:** <維持する挙動、互換性、運用上の制約。>
- **やらないこと:** <スコープ外。>

## 用語
- **<用語>**: <1〜2文の定義> _Avoid_: <使わない同義語>

## 決定事項
### ユーザー判断
- **D1** <判断>: <決定> — 理由: <1〜2文> — 却下: <案>: <理由>
### AI判断
- **A1** <判断>: <決定> — 根拠: <既存 pattern、制約、調査した事実>

## 未決事項
- **Q1** <判断> — <ユーザー判断に当たる理由>

## 設計
<責務配置、data flow、interface の単位で、決定事項を組み合わせた結果を書く。個々の判断理由は D / A の ID で参照する。>

## 変更面
<次の面のうち変更するものだけを書く: DB schema・データ移行、公開 interface（HTTP / GraphQL / 他モジュールから呼ばれる API / イベント）、依存関係、設定・環境変数・権限、非同期処理（job / スケジュール）。>
- <面>: <変更内容> (D2)
- 上記以外の面は変更しない。

## 展開順
<リリースや移行で守る順序。例: migration を適用してからコードを切り替える。>

## まれなケースの扱い
- <ケース> — <専用の処理> — <発生可能性と影響から専用の処理が必要と判断した理由>

## テスト方針
<追加・更新する test で検証する振る舞いと edge case、test と lint の command を書く。>

## リスク
- <リスク> — low | medium | high — <理由と手当て>

## スライス
- **S1** <タイトル> — approved | draft | outline — blocked_by: - — delivers: AC1, AC2

## タスク
<sliced では `### S1` のようにスライスごとの見出しを置き、outline のスライスは見出しと1行の概要だけにする。>
- [ ] **T1** <outcome を表すタスク名>
  - implements: AC1, D2
  - depends_on: -
  - done_when: <観測可能な完了条件。受入基準と同じ場合は AC の ID を書く。>
  - test: <検証する振る舞い> — `<command>`

## 影響範囲と既存パターン
<実装者が読み始める entry point、想定する変更箇所、踏襲する既存 pattern をパス付きで各1行書く。>

## AIレビュー
- 実行: <対象（全体 | S<N>）> / <reviewer / model / effort>、または 見送り: <理由>
- 信頼性: TRUSTED | UNTRUSTED | BLOCKED
- **F1** [P2] <指摘の要約> — 採用: <反映内容> | 見送り: <理由>

## 実行メモ
```

次のセクションは、該当する場合だけ置き、該当しない場合は見出しごと省く。

- `## 用語`: この作業で確定した、project 固有の用語があるとき。
- `## 未決事項`: draft の間でユーザー判断が残っているとき。空になったら見出しごと消す。
- `## 設計`: ユーザー判断があるとき、または局所的な low risk の変更でないとき。
- `## 展開順`: `## 変更面` に DB schema・データ移行または公開 interface があるとき。
- `## まれなケースの扱い`: 発生しにくい事象に専用の処理を入れるとき。
- `## スライス`: sliced のとき。
- `## AIレビュー`: G1 を通過した後。

`## 実行メモ` は見出しだけを置き、implement-plan の orchestrator だけが追記する。
`## タスク` のチェックボックスは implement-plan の orchestrator だけが更新する。

## タスク分解

plan.md は、plan.md だけを読む fresh session の上位モデルが、どこから読み始め、何ができたら完了かを判断できる粒度にする。
この粒度は file の列挙ではなく、entry point、既存 pattern、`done_when` で満たす。
1タスクは独立に検証できる outcome 1つにし、file やレイヤーの単位で分割しない。
`test` の振る舞いは `../../ai-review/references/test-selection-policy.md` に従って選ぶ。

`Risk` に応じて、次の粒度にする。

- low: タスクは通常1〜2個にする。`done_when` は受入基準の ID で書いてよい。`## 影響範囲と既存パターン` は entry point を数行で書く。
- medium: outcome ごとにタスクを分け、各タスクの `test` で targeted に検証できるようにする。
- high: `## 展開順` を `depends_on` で表し、`## 変更面` を具体的に書き、変更面に触れる変更を独立したタスクにする。

## 文体

plan.md はレビューする人間と fresh session の実装者が短時間で読めることを優先し、網羅的な説明書ではなく意思決定と作業の記録として書く。

- 「〜することができます」などの回りくどい語尾を使わず、「〜する」で言い切る。
- 却下した案の説明は、却下理由が伝わる最小限の長さにする。
- 自明なメリット・デメリットを書かない。
- 同じ主張を複数のセクションで繰り返さず、要件と決定事項は ID で参照する。
- やらないことに、スコープ外の一般論や将来の拡張可能性の羅列を書かない。
