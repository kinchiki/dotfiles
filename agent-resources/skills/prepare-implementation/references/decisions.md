# 調査と判断

Step 2 でコードベースを調べ、判断をユーザー判断と AI判断に分けて、ユーザー判断を質問するときに使う。

## 調査

read-only で実際の data flow を追い、影響するモジュール、既存 pattern、テストの慣習、repository の `CLAUDE.md` / `AGENTS.md` を確認する。
target repo が `app/interactions/` や `packs/` などの構成規約を持つ場合は、その構造を尊重する。
migration、後方互換性、permission / auth、N+1、バックグラウンドジョブの冪等性、API の公開範囲、i18n など、判断を生む edge を確認する。
タスクの entry point と想定する変更箇所もこの調査で特定し、plan.md の `## 影響範囲と既存パターン` に使う。
同じ repo の `.ai-local/plans/*/` にある過去の plan.md の `## 用語` があれば読み、今回の用語の照合に使う。

## 判断の分け方

実行可能で実質的に異なる選択肢がある判断だけを判断として扱う。
既存 pattern や制約から一意に決まる判断は、判断として扱わずに設計やタスクへそのまま書く。

次のいずれかに当たる判断はユーザー判断とし、`## 未決事項` に書いて質問する。

- 外から観測できる挙動や仕様が変わる。
- 互換性やデータに影響し、元に戻しにくい。
- スコープや優先順位の trade-off がある。
- コストや運用に影響する。

1 PR・1実装セッションに収まらない、または独立してリリースしたい段階がある場合は、スライスの分割方法をユーザー判断として聞く。
当たるか迷う判断は、ユーザー判断として扱う。
それ以外の判断は AI判断として AI が決め、根拠とともに `### AI判断` に書く。
AI判断は G1 のブリーフィングで見せ、異論があれば G1 で指摘を受ける。

## まれなケース

発生可能性と影響に見合う事象だけを専用の処理の対象にする。
低確率で単純なエラー処理で足りる事象は、単純なエラー処理で対処する。
発生しにくい事象に専用の処理を入れる場合だけ、`## まれなケースの扱い` に理由とともに書く。

## 質問ラウンド

`## 未決事項` のうち、他の未決事項の回答を前提にしない判断を1ラウンドにまとめて聞き、回答を待つ。
他の未決事項の回答を前提にする判断は、後のラウンドへ回す。
各問いには、既知の事実、判断が必要な理由、実行可能で実質的に異なる選択肢（最大3つ）とそれぞれの trade-off、推奨案とその理由を含める。
同じ設計 family の微修正版は1案にまとめ、既知の制約に反する案や明らかに劣る案を選択肢に含めない。

```text
### ラウンド <N>

❓ **Q1 - <問いのタイトル>**: <既知の事実、判断が必要な理由、選択肢と trade-off>

➡️ 推奨: <推奨案と理由>

---

❓ **Q2 - <問いのタイトル>**: <...>

➡️ 推奨: <推奨案と理由>
```

質問 UI がある環境で、問いが UI の上限に収まる場合は UI を使ってよい。

ラウンド中は次を行う。

- 問いに事実が必要な場合は、使えるなら sub-agent に調査させる。調査中の事実に依存する問いだけを待たせ、残りは先に聞く。
- ユーザーの用語が過去の `## 用語` とずれる場合や曖昧な場合は、正準の用語を提案して確認する。
- ユーザーの説明がコードと食い違う場合は、その食い違いを示して確認する。

回答を得たら、次を行う。

- 決まった判断を `### ユーザー判断` に移し、`## 未決事項` から消す。
- 確定した用語を `## 用語` に書く。
- 回答から生じた新しいユーザー判断を `## 未決事項` に加える。
- 組み合わせ案や再検討を求められた場合は、その観点を調べて選択肢を更新し、次のラウンドで改めて聞く。

`## 未決事項` が空になったら Step 3 へ進む。
