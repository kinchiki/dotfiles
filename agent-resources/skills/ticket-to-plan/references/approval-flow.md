# 承認フロー

Step 4 の草案レビューから Step 6 の最終承認まで使う。

## 草案レビュー

独立AIレビューの前に、実装プランの要約、タスク分解、ユーザー向け情報の草案を画面に表示してレビューを求める。
この時点の `AIレビュー` は未実施であることを明記する。
承認UIがある環境では、それを使う。

ユーザーの却下またはフィードバックは仕様として扱う。
フィードバックが前提を変える場合はコードベースを再調査する。
実装プランまたはタスク分解が変わる場合は更新版を再提示し、ユーザーレビュー完了後に独立AIレビューへ進む。

## 独立AIレビュー

ユーザーレビュー済みの最新草案に対して、`../../ai-review/SKILL.md` の plan review mode を実行する。
レビュー担当AIには計画AI、元の依頼内容、ユーザー確認済みの意図、維持する挙動、対象外、草案、選択した方針、選択根拠、受け入れた不利益、主要な棄却案と理由、調査した path を渡す。
レビュー担当AIは計画を編集せず、信頼性判定と指摘を返す。

同一計画に対する2回目以降の AIレビューでは、理由、対象、前回からの変更点を示してユーザーの明示的な確認を得る。
確認が得られない場合は再レビューを実行せず停止する。

## 指摘の採否

計画AIは全指摘の影響と対応案を整理し、項目ごとの採用または見送りをユーザーへ提示する。
ユーザーが採用を承認した指摘だけを実装プランとタスク分解へ反映する。
見送りが承認された指摘は、その理由とともにユーザー向け情報ファイルの `AIレビュー` に残す。

選択した方針の実現可能性、受入基準、重要なリスク、または比較の前提を実質的に崩す指摘は、その影響を明示する。
ユーザーがその指摘の採用を承認した場合は、計画AIが別方針へ変更せず `approach-selection.md` の方針選択へ戻る。
再選択後はタスク分解と草案を更新し、再レビューには既存の明示確認ルールを適用する。

P1 または P2 の採用で実装プランが実質的に変わる場合は、更新後の実装プランを再提示する。

## 最終承認

全指摘の判断が揃ったら、承認済みの変更だけを反映した実装プラン要約、タスク分解、ユーザー向け情報を提示して最終承認を得る。
AIレビューのレビュー担当AI、主要な指摘、計画AIの対応案、ユーザーの採否判断をユーザー向け情報の `AIレビュー` に記録する。

追加フィードバックは仕様として扱い、前提が変わる場合は再調査する。
実装プランまたはタスク分解が変わる場合は、変更の重要度に応じて独立AIレビューを再実行する。
最終承認されるまで計画を更新し、承認後も Step 8 の経路選択までは実装を始めない。
